## 2. 교차 환산 — v2 후보이지만 조건이 붙는다

### 왜 v1에서 하지 않았나

사글세와 전세·월세를 같은 잣대로 놓으려면 **기준 기간**을 정해야 하는데, 그 순간 서비스가 가정을 만들게 된다.

| 환산에 필요한 값 | 왜 우리가 정하면 안 되나 |
|---|---|
| 기준 기간 (1년? 2년?) | 사글세 계약 기간은 제각각이다. 6개월짜리를 1년 기준으로 펴면 **재계약을 1회 한다고 가정**한 것이 된다 |
| 재계약 시 금액 인상률 | 알 수 없다. 0%로 두는 것도 가정이다 |
| 중개보수 재발생 | 재계약 때 다시 드는지, 얼마인지 계약마다 다르다 |
| 전세금의 기회비용 | 사용자마다 다른 가정값. `FINANCE_ASSUMPTIONS`에 "반영하지 않았다"고 이미 명시했다 |

**화면에 뜬 숫자를 사용자는 "이 서비스가 알려준 기준"으로 받아들인다.** 위 네 값 중 하나라도 우리가 정하면 그때부터 서비스가 판정한 것이 된다 (R1·R8).
같은 이유로 2026-08-12에 `s-lien`의 "보증금 1,000만원" 기준과 전월세전환율 기본값을 각각 제거·거부했다.

### v2에서 하려면 무엇이 있어야 하나

**사용자가 가정을 직접 입력하고, 그 입력이 화면에 보일 때만** 가능하다. 전월세전환율(`cvRate`)을 다루는 방식이 이미 그 선례다 — 기본값 없이 사용자가 넣고, 넣기 전에는 계산하지 않는다.

- [ ] 기준 기간을 사용자 입력으로 받는다 (기본값 없음)
- [ ] "이 비교는 입력하신 N개월 기준입니다" 라벨을 결과에 항상 붙인다
- [ ] 재계약 횟수·중개보수는 **계산에 넣지 않고**, 빠졌다는 사실을 가정 문구에 적는다
- [ ] 입력이 없으면 환산 결과를 만들지 않고 절대값만 보여준다 (`calcPrepaid`의 `{ok:false}` 규약과 동일)

## 3. 기준 기간 · 피벗 비교

### 기준 기간

지금 비교 화면은 **월 단위 절대값**만 다룬다. 사글세는 "총액을 선납"하는 구조라 월 단위로 접으면 실제 부담(초기 목돈)이 안 보이고, 총액으로 두면 계약 기간이 다른 매물끼리 비교가 안 된다.

`calcPrepaid`가 두 값(`monthlyEquivalent`, `initialCash`)을 함께 돌려주는 것은 이 때문이다 — **한 숫자로 접지 않는다.** v2에서 기준 기간을 도입하더라도 이 두 값은 그대로 남겨야 한다.

- [ ] 계약 기간이 다른 매물을 나란히 놓을 때의 표기 규약 (프론트 판단 영역)
- [ ] "처음 드는 돈"과 "월 부담"을 한 축으로 합치지 않기

### 피벗 비교

현재 비교표는 **매물이 열, 항목이 행**이다. 거래유형이 4종으로 늘면서 유형별로 의미 없는 칸(사글세의 월세, 전세의 관리비 포함 여부 등)이 많아졌다.

- [ ] 유형이 섞인 비교에서 빈 칸을 어떻게 보일지 (`—` 유지 여부)
- [ ] 유형별로 행 묶음을 나눌지, 공통 행만 남길지
- [ ] **유형이 섞이면 환산하지 않고 절대값만 둔다**는 원칙은 어느 안에서도 유지

> 이건 표시 설계라 **프론트 세션 소유**다. 백엔드는 값만 내려준다.

## 4. 그 밖에 남은 사글세 관련 항목

- [ ] **AI 붙여넣기 파싱의 사글세 인식** — `lib/ai/normalize.ts`의 `DEAL_TYPES`에는 추가했지만, 프롬프트가 "사글세 300만원 6개월" 같은 표기에서 선납 개월·총액을 뽑아내는지는 **실측하지 않았다.** 못 뽑으면 사용자가 정보 확인 화면에서 채우면 되지만(설계상 정상), 얼마나 자주 놓치는지는 모른다

### 4-1. 붙여넣기 파싱 — 실측으로 확인된 두 가지 (2026-08-12)

둘 다 **발표 이틀 전이라 손대지 않았다.** `lib/ai/prompts.ts`를 건드리면 지금 잘 되는 것이 깨질 수 있고, 두 건 모두 정보 확인 화면에서 사용자가 고치는 설계 안에 있다.

#### ① 연식 — 모델이 자기 학습 시점을 현재로 가정한다

```
입력  "건물 연식 2009년"   →  출력  age: 15
2026년 기준이면 17이어야 한다. 모델은 ≈2024년을 현재로 보고 있다.
```

**이미 한 번 관측된 것과 같은 유형이다** — `docs/INFRA.md`에 `2008년 준공 → 16년차`(실제 18)로 기록돼 있고, **오차 폭도 2년으로 같다.** 두 번 관측됐으니 우연이 아니다.

- 검토할 방식: **프롬프트에 현재 연도를 주입**한다(`오늘은 {year}년이다. 준공년도가 주어지면 {year} - 준공년도로 계산하라`).
- 주의: `lib/ai/prompts.ts`는 순수 상수 파일이라 `Date.now()`를 그 안에서 부르면 안 된다(R2). 연도는 **호출부(라우트)가 넘겨야** 한다.
- 영향: **연식은 조사지 항목 선정의 입력값**이다(`v-mold` 10년차↑ · `v-window`·`v-boiler` 15년차↑). 2년 오차가 경계를 넘나들면 확인 항목이 달라진다.

#### ② `addressDetail` — 스키마에 아예 없다

```
입력  "대구대로 58길 37, 502호"  →  출력  address: "대구대로 58길 37, 502호"
                                        addressDetail: (없음)
```

`lib/ai/prompts.ts`의 응답 스키마에도, `lib/ai/normalize.ts`가 내보내는 필드 목록에도 `addressDetail`이 없다. 호수가 `address`에 붙어 들어온다.

- 고치려면 **프롬프트 스키마와 normalize 양쪽**에 필드를 추가해야 한다. 한쪽만 하면 모델이 준 값을 normalize가 버린다.
- R7(상세주소 미노출)에는 영향이 없다 — 노출 차단은 표시 단계에서 하고, 지금은 사용자가 정보 확인 화면에서 분리해 넣는다.

> **이 두 건은 발표 재료다.** "자동 취득 정보는 틀릴 수 있다"가 추상적 우려가 아니라
> **실제로 두 번 관측됐고**, 그래서 전 필드를 편집할 수 있는 정보 확인 화면을
> 반드시 경유하게 만들었다 (PRD §5.2). 설계가 먼저 있었고 관측이 뒤따라 그것을 뒷받침했다.
- [ ] **선납 개월 수의 현실적 상한** — 지금은 `int4` 상한까지만 막는다. `99999개월`도 통과한다. 화면 검증 영역이라 서버는 DB 한계까지만 본다 (연식과 같은 처리)
- [ ] **사글세 매물의 인쇄 레이아웃** — 헤더에 선납 정보를 넣을지. 현재는 `사글세 — · 22년차` 형태로 나온다
