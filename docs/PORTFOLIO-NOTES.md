## 1. 기술 선택과 근거

### 1.1 Vercel 함수 리전을 서울(icn1)이 아니라 싱가포르(sin1)로

**결론부터**: 사용자와 가까운 곳이 아니라 **DB와 가까운 곳**에 함수를 뒀다.

Neon에 **도쿄 리전이 없었다.** 한국에서 가장 가까운 선택지가 `ap-southeast-1`(싱가포르)이었고, 리전은 생성 후 변경이 불가능해 처음에 정해야 했다.

그다음이 판단 지점이다. 함수를 서울에 두면 사용자↔함수는 가깝지만 **함수↔DB가 매 쿼리마다 태평양을 건넌다.** 이 서비스의 Server Action은 한 번 호출에 DB를 여러 번 왕복한다 — 예를 들어 `saveVisitResults`는 `SELECT` → 병합 → `UPSERT`, `createProperty`는 `INSERT` → 규칙 선정 → `INSERT`다.

```
함수를 서울에 두면   사용자 →(가까움)→ 함수 →(멂)×N회→ DB
함수를 싱가포르에    사용자 →(멂)×1회→ 함수 →(가까움)×N회→ DB
```

**긴 구간을 N번 왕복하느냐, 1번만 건너느냐의 차이다.** 후자를 골랐다.

실제 배포본 응답 헤더가 이 구조를 그대로 보여준다.

```
X-Vercel-Id: icn1::sin1::…
             ↑엣지=서울  ↑함수=싱가포르
```

정적 자산은 서울 엣지에서, DB를 만지는 함수는 싱가포르에서 처리된다. 결과적으로 배포본 홈 응답이 **0.29~0.45초**로 로컬 프로덕션 빌드(0.53초)보다 빨랐다.

### 1.2 `git worktree`로 두 세션을 병렬 운영

프론트와 백엔드를 **같은 저장소의 다른 worktree**에서 동시에 굴렸다.

```
E:/project/recheck          main            백엔드 (액션 · API · 라우팅 · 지도 · DB)
E:/project/recheck-front    feat/screens    프론트 (components/screens/**)
```

**핵심은 디렉터리 소유권을 명시적으로 나눈 것이다.** 백엔드는 `components/screens/**`에 절대 쓰지 않고, 프론트는 `app/**`·`lib/actions/**`에 쓰지 않는다. 양쪽 인수인계 문서에 "쓰기 금지" 표를 박아 뒀다.

**결과: 병합 7회, 충돌 0건.** (`main…feat/screens` 사이 머지 커밋 9개, 코드 충돌 없음)

충돌이 안 난 이유는 운이 아니다.

- **타입을 계약으로 썼다.** 프론트가 `import type { CreatePropertyInput } from '@/lib/actions/properties'`처럼 백엔드 타입을 **직접 import** 했다. 시그니처가 어긋나면 `tsc`가 즉시 잡는다. 실제로 D3 연동 시점에 **props 불일치 0건**이었다.
- **새 콜백은 선택 prop으로 넘겼다.** 프론트가 `onDelete`·`onSetStatus`를 필수로 만들었다면 백엔드 코드가 즉시 컴파일 에러를 냈을 것이다. **선택 prop으로 두고 없으면 버튼을 렌더하지 않는** 방식이라, 빌드를 깨지 않고 기능을 넘기고 백엔드가 한 줄 연결하면 켜졌다.
- **문제를 발견해도 남의 디렉터리는 안 고쳤다.** 백엔드가 붙여넣기 탭의 버그 2건을 발견했을 때 코드를 고치지 않고 **재현 조건과 근거를 목록으로 넘겼다.** UI 흐름 판단이 어댑터로 흩어지는 것을 막기 위해서다.

### 1.3 Server Action에서 HTTP 상태 코드 대신 `ActionResult`

기획서(PRD §8.4)에는 "전이 규칙 위반 시 400"이라고 적혀 있었다. 그런데 **실제 구현은 Server Action이라 HTTP 상태 코드를 돌려줄 자리가 없다.** 문서가 Route Handler를 전제로 쓰인 것이다.

```ts
type ActionResult<T> = { ok: true; data: T } | { ok: false; error: string }
```

**왜 예외를 던지지 않았는가** — 이 팀의 프론트는 비전공자다. `try/catch`로 감싸는 걸 빠뜨리면 에러 바운더리가 떠서 흰 화면이 되고, 등록은 첫 단계라 사용자가 되돌아올 길이 없다. `ok`만 분기하면 되게 만들었다.

**그래서 생긴 제약**: 액션 안에서 예외가 새면 계약이 깨진다. 실제로 두 번 깨졌다.

1. 큰 숫자 입력 → Postgres가 `out of range` 예외 → 흰 화면 (§2.6에서 해결)
2. Server Action 자체가 예외로 실패(DB 장애 등) → 프론트가 `catch`로 값으로 바꿔 흡수

문서와 코드가 어긋난 채 두면 D3 연동에서 프론트가 헷갈리므로 **PRD와 CLAUDE.md 문구도 함께 고쳤다**(3곳). "구현을 문서에 맞추기"가 아니라 "문서를 사실에 맞추기"를 골랐다.

## 2. 실제로 잡은 버그

### 2.1 확정 파일에 박혀 있던 추정 좌표 — 3.9km 오차

**무엇을 발견했나.** 카카오 REST 키가 동작하는지 확인하려고 대구대 정문 주소(`경산시 진량읍 대구대로 201`)를 지오코딩했는데 **"정문에서 직선 3.4km"**가 나왔다. 정문 주소가 정문에서 3.4km 떨어져 있을 수는 없다.

```
lib/geo.ts  SCHOOL_ORIGIN   lat 35.8944      lng 128.8067
카카오 조회  경산캠퍼스        lat 35.90203…   lng 128.84884…
                                     두 지점 거리 = 3,890m
```

경도가 약 0.042도 어긋난 **추정값**이 상수로 박혀 있었다.

**왜 그렇게 판단했나.** `lib/geo.ts`는 "확정 파일 — 수정 금지"였다. 하지만 **"수정 금지"는 설계를 임의로 바꾸지 말라는 뜻이지 틀린 값을 보존하라는 뜻이 아니다.** 이 상수는 모든 매물의 `distance_from_school`에 캐시되므로, 틀린 채로 두면 홈 카드·비교 화면 위치 탭·조사지 PDF 헤더의 거리가 전부 틀어진다. 근거(출처·조회일)를 남기고 사용자 승인 후 교체했다.

**어떻게 재발을 막았나.** 세 겹으로 걸었다.

```ts
// tests/geo.test.ts — 좌표를 고정해 조용한 변경을 막는다
expect(SCHOOL_ORIGIN.lat).toBe(35.90203906952692);

// 캠퍼스 부지 안의 지점은 기준점에서 1km를 넘지 않아야 한다
// (이전 상수는 3.9km 떨어져 있었다)
expect(distanceFromSchool(35.904538973767, 128.842813264293)!).toBeLessThan(1000);
```

세 번째가 `tests/fixtures.test.ts`다. 상수를 바꾸자 **더미 데이터의 거리가 옛 값으로 남아 자기모순이 됐다** — 파일엔 `820m`인데 계산하면 `3,565m`였다. 그래서 더미 데이터의 숫자를 손으로 쓰지 않고 **실제 함수를 태워 생성**하도록 바꾸고, 정합성을 검사하는 테스트 19건을 추가했다.

> **일반화**: 확정 파일의 값이라도 실측으로 검증할 수 있으면 하라. "확정"은 임의 변경 금지이지 **검증 면제가 아니다.**

### 2.2 Gemini 추론 토큰이 출력 상한에 합산돼 JSON이 잘리던 것

**무엇을 발견했나.** `/api/ai/questions`가 **AI 호출은 성공했는데 질문 0건**을 반환했다. 에러도 없고 폴백도 안 탔다.

`ai_logs`에 남은 원문을 보니 답이 나왔다.

```json
[
  "겨울에 외풍이 심하지 않은지, 단열 상태는 어떤가요?",
  "난방 방식이 어떻게 되고, 겨울철 평균 난방비는 어느 정도 나오나요?",
  "창          ← 여기서 잘림
```

`usageMetadata`를 찍어 원인을 확정했다.

```
thoughtsTokenCount 803  +  실제 답변 65  =  868 / maxOutputTokens 1024
```

**Gemini 3.x는 추론(thinking) 토큰을 출력 상한에 함께 계산한다.** 여유가 156토큰뿐이라 답변이 조금만 길어지면 잘렸다. 잘린 JSON은 파싱에 실패하고, `normalizeQuestions(null)`이 빈 배열을 돌려주고, 라우트는 "변환된 질문이 없다"며 정상 종료했다.

**왜 코드만 봐서는 안 나오나.** 어느 줄도 틀리지 않았다. `try/catch`도 있고 폴백도 있다. **실패가 값으로 표현되지 않고 "성공했는데 결과가 비어 있음"으로 나타났기 때문**에 로직 리뷰로는 잡히지 않는다. 실호출 + 로그 대조로만 보인다.

**어떻게 막았나.** 두 겹이다.

- 상한을 4096으로 올려 여유 확보
- **`finishReason !== 'STOP'`이면 실패로 보고 다음 모델로 넘긴다** — 근본 방어다. 잘린 응답을 "성공"으로 받지 않는다

같은 조사에서 두 가지를 더 잡았다.

- **`gemini-2.5-flash` / `-lite`는 쓸 수 없다.** `404 "no longer available to new users"`. 5월 기준 지식으로 지정된 모델이었다. 사용 가능한 flash 계열을 전부 실측해 `gemini-3.5-flash`(3.7s) / `gemini-3.5-flash-lite`(1.1s)로 교체했다.
- **모델이 JSON 끝에 닫는 괄호를 하나 더 붙인다**(실제 관측). `parseJson`을 괄호 균형 스캔으로 바꿔 코드 펜스·앞뒤 설명문·문자열 안 괄호까지 처리하고, **잘린 응답은 확실히 `null`로 실패**시킨다. 테스트 8건으로 고정했다.

> **일반화**: LLM 연동에서 "성공했는데 결과가 비어 있음"은 가장 위험한 실패 모드다. 조용하고, 폴백도 안 타고, 사용자에겐 "AI가 아무것도 못 했다"로 보인다. `finishReason`을 반드시 확인하라.

### 2.3 RSC 페이로드에 상세주소가 실리던 것

**무엇을 발견했나.** 지도가 실제로 렌더되는지 확인하려고 페이지 HTML을 뜯어보다가 발견했다.

```
"addressDetail":"301호","visitChecks":[...전체...]
```

**화면에는 렌더되지 않는다.** 지도 핀에도, PDF에도 안 나온다. 그런데 **페이지 소스에는 그대로 있다.**

원인은 React Server Components의 동작이다. **서버 컴포넌트가 클라이언트 컴포넌트에 넘긴 props는 통째로 직렬화돼 HTML에 실린다.** 화면 컴포넌트 대부분이 `'use client'`라 `PropertyDTO`를 그대로 넘기면 동/호수와 조사지·질문 전체가 함께 실렸다.

**왜 고쳤나 — 규칙상 위반은 아니었다.** R7은 "지도 핀·PDF·공유 화면에 **렌더링하지 않는다**"이고, 렌더는 되지 않았다. 그래도 고친 이유는 하나다.

> 발표에서 개인정보 질문이 나왔을 때 "페이지 소스에는 남습니다"라고 답하고 싶지 않았다.

**어떻게 고쳤나.** 두 개의 투영 함수를 경계에 뒀다.

```ts
toMapProperties(properties)     // 지도에는 6개 필드만    (components/map/types.ts)
withoutAddressDetail(property)  // 화면에는 동/호수 제거   (app/_lib/property.ts)
```

**정보 확인·수정 화면만 예외다** — 거기서 사용자가 직접 편집하는 값이라 원본이 필요하다.

부수 효과로 페이지가 가벼워졌다: 더미 3건 기준 **12,890B → 9,169B (29% 감소)**. 조사지·질문 전체를 지도에 실을 이유가 없었다.

검증 결과 — 확인 화면 외 7개 화면에서 **잔존 0건**, 확인 화면은 편집 입력란에만 1건.

### 2.4 `order` 동점으로 그리드가 뒤바뀌어 한글이 세로로 쌓이던 것 *(프론트 세션)*

**무엇을 발견했나.** 홈 좌우 분할에서 목록이 340px 컬럼에 눌렸고, 그 좁은 폭에서 **"대구대학교"가 한 글자씩 세로로 쌓였다.**

**원인은 두 개가 겹친 것이다.**

1. `.rc-home-map`에만 `order`를 주고 `.rc-home-list`는 비워뒀다. 비워둔 쪽이 **기본값 `0`과 동점**이 되어 DOM 순서가 이겼고, 지도가 넓은 컬럼을 가져갔다.
2. 한글은 기본 설정에서 **음절 단위로 줄바꿈된다.** 폭이 모자라면 글자가 세로로 쌓인다. `word-break: keep-all`이 필요했다.

`min-width: 0`은 이미 있었고 원인이 아니었다 — **먼저 의심한 곳이 범인이 아니었다는 점**이 이 버그의 교훈이다.

**어떻게 막았나.** 프론트 인수인계 문서에 두 줄로 박았다.

> `order`는 관련된 것을 **전부** 지정할 것 — 하나만 주면 나머지가 기본값 0과 동점이 된다
> `word-break: keep-all`은 장식이 아니다 — 지우지 말 것

### 2.5 붙여넣기 분기 ②가 도달 불가능한 죽은 코드였던 것

**무엇을 발견했나.** 프론트가 "파싱은 됐는데 저장이 거부된 경우 값을 보존한다"는 분기를 추가했다. 백엔드가 그 분기를 검증하려고 **실패시킬 입력을 찾다가 못 찾았다.**

`createProperty`가 거부하는 조건은 두 개뿐이다.

```ts
name 비어 있음   →  화면이 `data.name?.trim() || '붙여넣은 매물'`로 기본값을 넣는다
dealType 무효    →  앞 분기가 이미 걸러낸다
```

**클라이언트가 서버 검증 대상 두 필드를 모두 보장하므로, 어떤 입력으로도 이 분기에 도달할 수 없었다.**

**왜 이게 중요한가.** 고치려던 문제("저장 거부 시 값이 버려진다")가 **실제로는 다른 경로에서 일어나고 있었다.**

```
"진량읍 원룸입니다. 23제곱미터, 3층, 지역난방, 2015년 준공. 관리비 6만원."
  → address · heating · mgmtFee · area · age · floor  6개 인식
  → dealType 없음 → 실패로 처리 → 6개 전부 폐기 + "자동 인식에 실패했어요"
```

거래유형이 안 적힌 매물 설명은 흔하다. **"AI가 읽었는데 아무것도 안 채워진" 화면**이 나온다.

**어떻게 고쳤나.** 프론트가 분기를 셋으로 나눴다.

```
① 아무것도 못 읽음        → 빈 폼 + 안내
② 거래유형만 없거나 무효   → 읽은 값을 채우고 거래유형만 고르게    ← 신설
③ 전부 읽음               → 등록
```

**거래유형은 추측해서 채우지 않는다.** 조사지·안전 점검 항목 선정의 입력값이라 틀리면 항목이 통째로 어긋난다(R8).

> **일반화**: "성공/실패 이분법"으로 나누면 **부분 성공을 실패로 처리**하게 된다. 죽은 코드를 발견했다면 "왜 도달할 수 없는가"를 되짚어라 — 대개 진짜 문제는 옆에 있다.

### 2.6 큰 숫자 입력이 예외로 터지던 것

보증금 칸에서 `0`을 길게 누르면 재현됐다.

```
price = 2,147,483,648   →  NeonDbError: value out of range for type integer
area  = 99,999.99       →  numeric field overflow
```

액션이 `ActionResult` 대신 **예외를 밖으로 내보내** 프론트가 흰 화면을 만났다. §1.3에서 세운 계약이 깨진 것이다.

`checkLimits()`를 INSERT/UPDATE 전에 두고 DB 타입 한계에서 걸렀다. **음수는 다르게 다룬다** — `0`으로 보정한다. "-5를 입력했더니 저장이 안 된다"보다 "0으로 들어갔다"가 덜 막힌다.

## 3. 제품 원칙이 코드가 된 지점

이 서비스의 원칙은 문서에만 있지 않다. **각 원칙이 코드 어디에서 강제되는지** 정리했다.

### R1 — AI는 판정하지 않는다

**이중 장치다.** 프롬프트만으로는 새기 때문이다.

```
① 프롬프트 가드레일   lib/ai/prompts.ts — 세 프롬프트 모두 "판단하지 말라"를 명시
② 출력 필터          containsBanned() 통과 후에만 사용자에게 노출
③ 정규화             normalizeParsed()가 아는 키·아는 타입만 통과시키고
                     판정성 표현이 섞인 필드는 버린다
```

**실제 출력** — 붙여넣기 탭에 판정성 텍스트를 넣었을 때:

```
입력:  "이 매물 진짜 좋아요 강력 추천합니다 안전합니다"
출력:  {"ok":false,"reason":"인식된 항목이 없습니다. 직접 입력해주세요."}
```

**한 필드도 통과하지 못한다.** "AI가 판정을 못 하게 막았다"는 주장을 화면에서 증명할 수 있다.

테스트로도 고정했다 — 금융 문구·핀 라벨·협상 질문 템플릿이 전부 `containsBanned()`를 통과하는지 검사한다.

### R5 — 현장 항목은 방문 후에 체크한다

**두 곳에서 구현됐고, 둘 다 "하지 않은 것"이다.**

**① 조사지 화면에 현장 항목 체크박스가 없다.** 국면 A는 "확인할 목록"만 만든다. 검증해 보니 조사지 화면의 체크박스 21개는 **전부 질문 은행 선택용**이고, 현장 항목은 제목·설명과 `×`(제거) 버튼만 렌더된다. 서버도 같은 원칙이다 — `addVisitCheck`는 `result`를 항상 `''`로 생성한다.

**② 방문 기록에 자동 저장을 쓰지 않았다.** *(프론트 세션 판단)*

이게 더 미묘하다. `saveVisitResults`는 결과가 하나라도 들어오면 `markRecordedIfNeeded()`로 **`ready → recorded` 전이를 일으킨다.** 자동 저장을 넣으면:

```
4택 버튼을 한 번 누름
  → 자동 저장
  → 매물이 "기록 완료"로 바뀜
  → 국면 C(안전 점검)가 열림
  → 절반만 기록한 매물이 계약 단계로 올라감
```

**"편의 기능"이 시점 원칙을 무너뜨린다.** 그래서 `[기록 저장]` 일괄 저장을 유지하고, 대신 입력 유실을 막는 **이탈 경고**를 붙였다.

### R8 — 추측한 사실을 코드나 문구에 넣지 않는다

**① 전월세전환율에 기본값을 넣지 않았다.**

법정 전환율은 기준금리에 연동되어 시점에 따라 바뀐다. 그런데 그보다 중요한 이유가 있다.

> 화면에 숫자가 미리 떠 있으면 사용자는 그것을 **"이 서비스가 알려준 기준"**으로 받아들인다. 그 순간 서비스가 기준을 제시한 것이 되고, 판정하지 않는다는 원칙이 깨진다.

입력 필드는 빈 값이 기본이고, 미입력 시 계산 결과 대신 **"전환율을 입력하면 참고 계산이 표시됩니다"** 안내만 나온다. 그리고 계산이 나오든 안 나오든 **"법정 전환율은 갱신 계약의 상한 기준이며 신규 계약 협상에는 강제력이 없습니다"**를 상시 노출한다.

**② 실경로 도보시간 대신 직선거리를 쓰고 "직선거리 기준 추정"을 병기한다.**

카카오 길찾기는 유료 API이고, 이 프로젝트는 "유료 API 사용 안 함" 상태다. 한도 초과 시 **과금이 아니라 호출 차단**이므로 학생 프로젝트에서 의도치 않은 청구가 생기지 않는다 — 그 안전장치를 뒤집을 만한 이득이 아니라고 판단했다.

**중요한 건 "정확한 값을 못 구했으니 대충 쓴다"가 아니라 "구한 값이 무엇인지 정확히 말한다"이다.**

```ts
formatDistanceLabel(582)
// "대구대학교에서 직선 582m (도보 약 9분 · 직선거리 기준 추정)"
```

`formatDistanceLabel()` 하나가 기준점 이름과 "추정" 병기를 함께 관리한다. 화면이 문구를 조립하면 어딘가에서 빠지므로, **조립할 기회를 주지 않았다.**

같은 이유로 기준점 표기도 다듬었다. 좌표는 캠퍼스 중심(POI)이지 정문이 아니므로 **"정문"이라고 쓰지 않는다.** 테스트가 `name`에 `정문`이 들어가면 실패시킨다.

**③ 기회비용을 계산에 넣지 않고 "반영하지 않았습니다"로 명시했다.**

전세와 월세를 비교할 때 월 주거비만 보면 왜곡이 생긴다.

```
월세 A:  월 주거비 50만 / 초기 자기자금   500만
전세 B:  월 주거비 17만 / 초기 자기자금 4,500만   ← 4,000만이 묶임

기회비용 3% 가정 시   51.3만  vs  28.3만        (3배 → 1.7배로 좁혀짐)
```

**기회비용을 계산에 넣으면 비교가 훨씬 정확해진다. 그래도 넣지 않았다.**

> 기회비용률은 사용자마다 다른 가정값이다. 서비스가 그 숫자를 정하면 **"이 서비스의 기준"**이 된다.

대신 `FINANCE_ASSUMPTIONS`에 **계산이 하지 않는 것**을 명시했다. 적지 않으면 사용자는 들어 있다고 가정한다.

```
가정: 이자만 상환 방식, 월 주거비 = 월세 + 관리비 + 대출 월이자.
중개보수·이사비 등 초기 부대비용은 포함되지 않았습니다.
보증금·전세금으로 묶이는 자금의 기회비용은 반영하지 않았습니다.
매매는 상환 구조가 달라 이 계산에서 제외됩니다.
```

화면은 대신 **초기 자기자금과 월 주거비를 같은 비중으로** 보여준다. 판단 재료를 나란히 놓고 결론은 내지 않는다.

**⚠ 부족** 표시도 같은 원칙이다 — "초기 필요자금이 보유 현금보다 큼(**산술적 사실 표시이며 판정이 아닙니다**)".

### 상태 전이는 서버가 강제하고, UI는 잠금 이유를 함께 보여준다

```
prep → ready → recorded → confirmed
         ↘ excluded ↗ (복구 시 prep)      confirmed → recorded (확정 취소)
```

전이 판단은 **`canTransition()` 한 곳**에서만 한다. 화면이 아니라 서버가 거부한다.

**하지만 서버가 막는 것만으로는 부족하다.** 사용자에게는 "왜 안 되는지"가 보여야 한다.

```
[A 방문 준비 ✓]  [B 방문 기록]              [C 계약]
                  조사지를 완성하면 열립니다    조사지를 완성하면 열립니다
```

`prep` 상태의 매물에서 안전 점검 화면에 들어가면 **286자짜리 잠금 화면**이 뜬다(정상 매물은 1,825자). 비교 화면에서는 기록이 없는 매물에 **"방문 기록 먼저 입력"**이 붙는다.

프로토타입에 있던 **"방문 기록으로 건너뛰기" 버튼은 삭제했다.** 서버가 `prep → recorded`를 거부하기도 하고, 조사지 없이 방문 기록을 쓰는 것 자체가 R5 위반이다. **UI에 있는데 서버가 막는 버튼**은 사용자에게 최악이다.

## 4. 발표 시연 후보

전부 실제 관측된 출력이다.

### ① AI 차이 요약 — 우열 없이 사실 차이만

비교 화면의 `[차이점 AI 요약]`. AI가 판정으로 미끄러지기 가장 쉬운 지점이다.

> "진량 투룸 B는 전세 매물로 수압, 소음, 채광, 보일러 작동 상태를 확인하고 난방비와 소음 민원 관련 답변을 얻었으나, 대구대 원룸 A는 월세 매물로 아직 현장 확인이나 답변을 받은 기록이 없습니다. 진량 투룸 B의 미확인 항목은 옵션 가전 작동, 엘리베이터 유무, 주차 및 자전거 보관 위치, 쓰레기 배출 방식, 반려묘 사육 가능 여부입니다. …"

**"어느 쪽이 낫다"가 한 줄도 없다.** 기록된 사실의 차이와 각 매물의 미확인 항목만 서술한다. `containsBanned()` 필터도 통과했다.

### ② "2008년 준공 → 16년차" — 정보 확인 화면이 존재하는 이유

붙여넣기 파싱이 10개 필드를 정확히 뽑아냈는데, **연식만 틀렸다**(2026−2008=18이 정답).

```json
{"name":"경산 진량읍 대구대 앞 원룸","dealType":"월세","price":45,"deposit":500,
 "mgmtFee":5,"area":23,"age":16,"heating":"개별난방","floor":"2"}
```

다른 입력에서도 재현됐다 — `"2021년 준공" → age: 3`(정답 5).

**이게 왜 좋은 시연 소재인가.** PRD §5.2가 "자동 취득 정보는 틀릴 수 있으므로 전 필드 편집 가능한 확인 화면을 반드시 경유"라고 정한 것이 **추상적 우려가 아니라 실제로 일어나는 일**임을 보여준다. 그리고 연식은 조사지 항목 선정의 입력값이라(`v-mold`는 10년차↑, `v-window`는 15년차↑) 틀리면 조사지가 통째로 어긋난다.

> "AI가 읽고, 사람이 확인하고, 규칙이 정한다" — 세 층이 왜 필요한지 한 장면으로 설명된다.

### ③ R1 차단 — 판정성 텍스트를 넣었을 때

```
붙여넣기 탭 입력:  "이 매물 진짜 좋아요 강력 추천합니다 안전합니다"
결과:            {"ok":false,"reason":"인식된 항목이 없습니다."}
```

**한 필드도 통과하지 못한다.** (§3 R1 참조)

### ④ 외부 의존성이 죽어도 흐름이 안 끊긴다

| 무엇이 죽으면 | 어떻게 되나 |
|---|---|
| Gemini | 질문 은행 폴백 — `{"ok":false,"questions":[3건],"source":"template"}`. 출처 배지만 AI → 규칙 기반으로 바뀐다 |
| 카카오 지도 SDK | 리스트 뷰로 대체 + 하단 고정 문구 유지 |
| 좌표 획득 | `latitude` null 저장 → "위치 미지정" 그룹. **등록은 성공한다** |
| Neon | 액션이 예외를 값으로 바꿔 화면 안에서 처리 |

**"우리 지도에는 우리가 추천하는 매물이 없습니다. 사용자가 직접 가져온 후보들만 있습니다."**

### ⑤ 카카오 도메인 제한이 실제로 작동한다 (보안 질문 대비)

`NEXT_PUBLIC_KAKAO_MAP_KEY`는 클라이언트 번들에 노출된다. "키가 공개되는데 괜찮냐"는 질문에 대한 답이다.

```
Referer https://recheck-home.vercel.app/     HTTP 200  스크립트 반환
Referer http://localhost:3000/               HTTP 200  스크립트 반환
Referer https://not-registered.example.com/  HTTP 401  {"errorType":"AccessDeniedError",
                                                       "message":"domain mismatched!"}
```

**서버 전용 키(`GEMINI_API_KEY`·`KAKAO_REST_KEY`·`DATABASE_URL`)는 `'server-only'` import로 클라이언트 번들 유입 시 빌드가 실패하도록 막았다.** 저장소도 키를 다루기 전에 private으로 전환했다 — 봇이 public 저장소를 상시 스캔해 커밋 직후 수집하기 때문이다.

## 5. 검증에 대해 — 무엇을 확인했고 무엇을 못 했는가

포트폴리오에서 이 절이 빠지면 나머지가 약해진다.

### 확인한 것

- **테스트 114건** — DB 없이 실행. 순수 함수(거리·금융·규칙), AI 가드레일, 더미 데이터 정합성
- **실 DB 통합 검증** — `next/headers`만 대체하고 실제 Neon에 붙여 Server Action 전 경로를 태웠다(소유권 격리, 상태 전이 거부, 잘못된 값 정규화, CASCADE)
- **프로덕션 빌드 + HTTP로 렌더된 HTML 검사** — 필수 문구, 수치 정합성, R5·R7 준수
- **배포본 실호출** — 시나리오 8단계, AI 3종, 세션 분리, 도메인 제한

### 확인하지 못한 것

**브라우저 자동화 도구가 없었다.** 그래서 다음은 사용자가 직접 확인했다.

- 클릭·입력 등 DOM 상호작용
- 카카오 지도 **타일이 실제로 그려지는지**
- `window.print()` **인쇄 미리보기 모양**
- 클라이언트 상태 변화(폼이 채워졌는지, 스피너가 풀렸는지)

특히 하나는 명시해 둘 가치가 있다. **중복 요청 방지(`useMutations`)는 클라이언트 가드라, 서버에서 액션을 직접 부르면 우회된다.** 서버 테스트에서 중복이 그대로 생기는 것을 보고 "동작한다"고 보고하지 않았다 — 코드 판독 결과와 런타임 미검증 사실을 나눠서 보고했다.

> 검증 방법의 한계를 알고 **"확인하지 못했다"고 쓰는 것**도 결과의 일부다.

## 6. 아직 남은 것

정직하게 적는다.

| 항목 | 상태 |
|---|---|
| 동시 요청 중복 | 서버는 막지 않는다. 클라이언트 가드에만 의존. 발표까지 사흘 남은 시점에 **스키마 마이그레이션 리스크를 지지 않기로** 결정 |
| Gemini 무료 티어 RPM/RPD | 미확인. **이 값에 의존하는 제한 로직을 넣지 않았다** — 모르는 수치로 코드를 쓰지 않는다는 R8의 적용 |
| 카카오 로컬 API 일일 한도 | 미확인. 지도 SDK의 300,000회는 로컬 API에 적용되지 않는다 |
| `age` 현실적 상한 | DB 한계(21억)까지만 막는다. `99999년차`도 통과 |

**MVP에서 의도적으로 뺀 것**(Won't = 로드맵): 로그인 · 사진 첨부 · 공유 링크 · 핀 클러스터링 · 실경로 도보시간 · 링크 크롤링 · 등기부 OCR · 리뷰(UGC)

리뷰는 **콜드스타트 문제**로 뺐다. 링크 크롤링은 **약관 위반**이라 뺐다 — 사용자가 직접 복사해 붙여넣은 텍스트 파싱만 허용한다.

## 7. 한 장 요약

> **판정 가능한 것은 전부 규칙이 처리한다.** 확인 항목 선정·거리·금융·진행률·상태 전이는 순수 함수다. 같은 입력이면 항상 같은 출력이고, 유닛 테스트 대상이다.
>
> **AI는 자유 텍스트 이해가 꼭 필요한 3지점에만 쓴다.** 붙여넣기 구조화 / 우려→질문 변환 / 기록 차이 요약. 그 외에는 쓰지 않는다 — "규칙으로도 되는데 AI를 쓰는" 코드는 작성하지 않았다.
>
> **판단은 사용자가 한다.** 그래서 점수도 랭킹도 추천도 없다. 계산이 하지 않는 것까지 화면에 적는다.
>
> **어떤 외부 의존성이 죽어도 핵심 검증 흐름은 동작한다.** 실패는 예외가 아니라 `{ok:false}`이고, 모든 외부 호출에 폴백이 있다.
