## 2. 기기 OCR — 최대 단일 위험 (보류)

> **2026-09-29 보류.** 1순위 경로는 pdf.js 텍스트 레이어 직접 추출이다. Tesseract.js 도입은 별도 승인. 아래 실측값과 설계는 재개할 때를 위해 남긴다.

### 2-1. 자산 용량 [실측 2026-09-09]

| 파일 | 크기 |
|---|---|
| `tessdata/kor.traineddata` (표준) | **14.61 MB** |
| `tessdata/eng.traineddata` (표준) | **22.38 MB** |
| `tessdata_fast/kor.traineddata` | **1.60 MB** |
| `tessdata_fast/eng.traineddata` | **3.92 MB** |
| `tessdata_best/kor.traineddata` | 11.95 MB |
| `tesseract.js-core` 런타임 wasm (`simd-lstm`) | **2.74 MB** |
| `pdfjs-dist` worker (min) | **1.21 MB** |

**함정**: 아무 생각 없이 `kor+eng` 표준판을 쓰면 첫 로드에 **37MB**가 내려간다. 모바일 4G에서 첫 화면이 죽는다.

**결정 권고** (보류 전 기준 — 재개 시 적용)
- 언어 데이터는 **`tessdata_fast/kor` 하나(1.6MB)**로 시작한다. `kor.traineddata`는 라틴 문자·숫자를 포함하므로 `eng` 없이 먼저 실측하고, 영문 인식이 실제로 문제일 때만 `fast/eng`(3.92MB)를 더한다.
- wasm 코어는 `simd-lstm` 변형(2.74MB)을 명시적으로 지정한다. 기본 선택에 맡기면 비-LSTM 3.31MB가 붙는다.
- ~~첫 로드 예산: pdf.js 1.2 + wasm 2.74 + kor fast 1.6 ≈ 5.5MB~~ → **현행 예산 2.0MB** (2026-09-29). pdf.js worker 1.21MB만 들어간다. Tesseract(wasm 2.74 + kor fast 1.60 = 4.34MB)를 다시 넣으려면 예산 초과이므로 승인 필요.
- 자체 호스팅(`public/tessdata/`)은 맞는 결정이다 — CDN 의존이 없어야 R4의 "오프라인에서 동작"이 성립한다. Service Worker 캐시에 넣어 2회차부터 0바이트로 만든다.

> 이 규칙은 `CLAUDE.md` 기술 스택 절에 못 박아 둔다. AI 코딩 세션은 튜토리얼 기본값(`kor+eng` 표준)을 그대로 쓴다.

### 2-2. 처리 시간 [미확인 — 보류 중 측정 안 함]

A4 300dpi 한 페이지를 모바일 CPU에서 Tesseract로 돌리면 **수십 초** 단위가 될 수 있다 [추정]. 등기사항전부증명서는 보통 2~5쪽이다 [추정]. 전 페이지 OCR은 실사용에서 못 쓴다.

**완화 순서**
1. **텍스트 레이어 우선.** 있으면 OCR을 아예 건너뛴다. 이게 되면 위 리스크 절반이 사라진다
2. 필요한 페이지만 (표제부·갑구·을구가 있는 앞쪽)
3. 렌더 배율을 낮춰 실측 — 인식률과 시간의 교환비를 표로 남긴다
4. Web Worker로 UI 블로킹 방지 + 진행률 표시

### 2-3. 한국어 정확도 [미확인 — 보류 중 측정 안 함]

Tesseract 한국어는 라틴어권 대비 약하고, 등기부는 **표 레이아웃**이라 문자 인식과 별개로 구조가 깨진다. 촬영본은 기울기·조명까지 더해진다.

**분기 판정**

## 3. 대조 엔진 — 정규화가 본체

### 3-1. 무난한 것
㎡↔평(3.3058), 금액 단위(억/만원/원, `₩`, 쉼표), 성명 공백 제거, 층 표기(`2층`/`제2층`/`2F`). 전부 순수 함수 + 테스트.

### 3-2. 주의해야 할 것

**① 한글 금액 파서** — `"일금 삼천만원정"` → `30000000`. 반나절. 십/백/천/만/억 자릿수 처리와 `정`·`원` 접미 제거. **문서 내부 대조(계약서 한글↔숫자)의 전제**라 여기가 틀리면 대표 대조 항목 하나가 죽는다. 테스트 케이스를 20개 이상 둔다.

**② 주소 — `different`를 함부로 내지 말 것** ⚠

가장 위험한 자리다. 광고는 보통 지번·동네 이름, 등기부 표제부는 도로명+지번, 계약서는 도로명. **표기 체계가 달라서 다른 것**을 "다르게 기재되어 있습니다"로 내보내면 오탐이 쏟아지고, 그 순간 서비스 신뢰가 무너진다.

권고:
- 주소는 **`same`/`missing`만 판정하고 `different`는 내지 않는다.** 정규화 후 일치하면 `same`, 아니면 **"확인 필요 — 두 표기를 나란히 보여줌"**이라는 제3의 상태로 표시한다
- `different`를 내는 항목은 **표기 체계가 같은 것**으로 한정한다: 성명, 금액, 면적, 용도, 층, 날짜
- V2-PLAN §4-1의 "목적물 표시 ↔ 표제부"는 소재지·면적·용도 세 항목으로 쪼개져 있는데, **소재지만 위 규칙을 따로 적용**한다

이건 R1의 연장이다. 판정하지 않는 서비스가 오탐을 내면 판정하는 서비스보다 나쁘다.

**③ `different`의 정의를 문서화** — `null` vs 빈 문자열 vs `"없음"`. `missing`은 "그 문서에 그 필드가 원래 없음"(예: 광고에 소유자)과 "있어야 하는데 못 찾음"이 다르다. 후자는 **확인 화면에서 사용자가 채울 수 있어야** 하므로 두 상태를 구분한다. `document_fields.edited_by_user`가 이미 있으니 여기에 `not_applicable`을 더한다.

## 4. 오프라인 조사지 — 가장 과소평가된 항목

### 4-1. 문제

Next.js App Router에서 서버 컴포넌트로 그려지는 페이지는 **오프라인에서 열리지 않는다.** Service Worker로 RSC 페이로드를 캐시하는 방법이 있긴 하나 취약하고, 데이터가 최신이라는 보장이 없다.

즉 "PWA + 오프라인 조사지"(V2-STATUS 6단계)는 다음을 포함한다:

1. 조사지 화면을 **클라이언트 컴포넌트**로 전환 (또는 클라이언트 렌더 경로를 하나 더 만든다)
2. 온라인일 때 조사지 데이터를 **IndexedDB에 미러링**하는 동기화 로직
3. Service Worker로 앱 셸·정적 자산 캐시
4. 입력 큐 → 온라인 복귀 시 Server Action 재전송

**②가 핵심 공수다.** ①③④는 정형이다.

### 4-2. 권고

- **범위를 조사지 1화면으로 못 박는다.** "방문 기록도"까지 넣으면 두 화면의 데이터 소스를 전환해야 한다. V2-PLAN은 "조사지·방문 기록"이라 적혀 있는데, 실측 후 조사지만 남기는 선택지를 열어 둔다
- `next-pwa` 류 래퍼는 App Router 지원이 들쭉날쭉하다. **Service Worker를 직접 쓴다** — 캐시 대상이 앱 셸 + pdf.js worker 정도로 작다 (tessdata는 보류)
- 완료 기준은 "비행기 모드에서 조사지가 열린다" 한 장면이다. 그 한 장면이 성립하는 최소 경로만 만든다

### 4-3. iOS Safari 제약 [미확인 — 실기기 확인 항목]

- 홈 화면 추가한 PWA와 Safari 탭은 저장소가 분리될 수 있다 → **"홈 화면에 추가한 뒤 문서를 올리세요"** 안내 순서가 중요
- 장기 미사용 시 저장소가 회수되는 정책이 있다 → **원본 PDF·이미지가 사라질 수 있다**. "원본은 이 기기에만 있고 지워질 수 있습니다"를 UI에 적는다. 이건 R9의 반대급부이고 숨기면 안 된다
- 실기기 1대에서 반드시 확인한다. 안드로이드만 보고 넘어가면 실사용자 기기에서 터진다

## 5. 서버 경계의 하드 리밋

### 5-1. Vercel 함수 요청 본문 4.5MB [문서 확인]

Vercel 함수의 요청·응답 본문 상한은 **4.5MB**이고 넘으면 `413 FUNCTION_PAYLOAD_TOO_LARGE`가 반환된다(Vercel 공식 문서).

`POST /api/ocr {imageBase64}`(서버 OCR — 보류)는 **base64가 원본의 약 1.33배**라 원본 3.3MB가 실질 상한이다. 요즘 폰 사진은 2~6MB이므로 **그대로 보내면 절반은 실패한다.**

→ 클라이언트에서 보내기 전 반드시 축소: 장변 2000px, JPEG 품질 0.7 정도면 대개 300~800KB. `lib/client/ocr.ts`에 축소 함수를 두고 **축소 후 크기를 로그에 남긴다.**

### 5-2. Server Action 본문 1MB [문서 확인]

Server Action의 요청 본문은 **기본 1MB**이며 `next.config.js`의 `serverActions.bodySizeLimit`으로 조정한다(Next.js 공식 문서).

오프라인 큐가 쌓였다가 한 번에 재전송되면 걸릴 수 있다. **큐는 항목 단위로 순차 전송**하고, 한 번에 묶지 않는다. 묶어야 한다면 상한을 명시적으로 올리되 이유를 주석에 남긴다.

### 5-3. 함수 실행 시간 [미확인 — 서버 OCR 보류 중 측정 안 함]

Gemini 이미지 입력은 텍스트보다 응답이 느리다. 서버 OCR 라우트의 `maxDuration`을 확인하고 실측한다. **타임아웃도 폴백으로 처리한다** — 200 + `{ok:false}` 규약 유지, 사용자에게는 "수기 입력" 경로.

### 5-4. ⚠ 문서 모순 — 서버 OCR에서는 마스킹이 불가능하다 (경로 보류, 원칙 유지)

V2-PLAN·CLAUDE-v2는 "서버로 보내는 텍스트는 주민번호·생년월일을 마스킹한다"고 적었다. 이건 **지점 ④(텍스트 구조화)에만 성립**한다.

서버 OCR 폴백은 **이미지를 통째로** 보낸다. 읽기 전에는 무엇이 주민번호인지 알 수 없으므로 **가릴 수 없다.** 이 경로에서 마스킹은 원리상 불가능하다.

→ 조치 세 가지:
1. 동의 다이얼로그에 명시한다: *"서버로 문서 이미지가 전송됩니다. 이미지는 처리 후 저장되지 않지만, 이미지 안의 개인정보를 미리 가릴 수는 없습니다. 가리고 촬영하거나 수기 입력을 선택하실 수 있습니다."*
2. 동의 화면에 **"주민번호가 보이면 가리고 다시 찍기"** 안내와 수기 입력 버튼을 나란히 둔다
3. `CLAUDE.md` R9에 이 예외를 명시한다. 지금 문구는 코딩 세션이 "이미지도 마스킹하라"는 불가능한 지시로 읽는다

이 모순을 먼저 드러내는 것이 "온디바이스 경계를 스스로 그은" 구체적 증거다.

## 6. 구조 검토

### 6-1. 잘 잡힌 것

- **`lib/compare/*`를 순수 함수로 분리** — R2가 규칙이 아니라 구조로 강제된다. "다른가는 코드가 정한다"가 파일 경계로 보인다. v2 설계에서 가장 잘한 결정
- **`lib/ai/touchpoints.ts` 단일 소스** — 지점이 3→5로 늘 때 등록제로 바꾼 것은 맞다. 대시보드의 규칙:AI 비율을 지점별로 쪼갤 수 있다
- **`documents`에 원본 참조 컬럼 없음** — R9가 스키마로 강제된다. 코드 리뷰 없이도 위반이 불가능한 형태
- **`visits`를 지금 1행으로 미리 생성** — 나중 1:N 대비. 나중에 하는 것보다 싸다
- **`discrepancies`가 원문 값을 함께 저장** — 재계산 가능하고 감사 가능

### 6-2. 손볼 곳

**① `document_fields`의 타입 안전성**

`field_key · value` 형태는 EAV라 TypeScript가 지켜주지 못한다. `lib/compare/schema.ts`에서 `field_key`를 union 타입으로 정의하고, DB 읽기 지점에서 런타임 검증(zod 등)을 한 번 통과시킨다. 안 하면 오타 하나가 조용히 `missing`으로 나타난다.

**② 대조 결과의 idempotency**

대조를 다시 돌릴 때 `discrepancies`가 중복되지 않아야 한다. **`property_id` 기준 전량 삭제 후 재삽입**이 가장 단순하다. 단 `discrepancies → questions` 연결이 있으므로, 질문은 별도 테이블에 남기고 삭제 시 연결을 끊지 않는 설계로 한다(질문에 원본 값 스냅샷을 복사해 둔다).

**③ 클라이언트/서버 번들 경계** ⚠

`lib/client/*`(PDF 추출·보류된 OCR)가 서버 번들에 딸려 들어가면 빌드가 커지고 최악의 경우 서버에서 wasm 로드를 시도한다. Next.js에서 흔한 사고다.
- `lib/client/*`는 전부 `'use client'` 파일에서만 import
- Tesseract·pdf.js는 **동적 import**(`await import('tesseract.js')`)로 실제 사용 시점에 로드
- 빌드 후 번들 크기를 한 번 확인하고 `[러너 실측]`으로 보고

**④ `special_terms` 원문 표시와 R7**

특약 원문에는 임대인·임차인 성명과 **상세주소(동/호수)**가 그대로 들어 있다. 원문 그대로 표시하면 R7(상세주소 미노출)과 충돌한다.
→ 특약은 **인쇄·공유 화면에서 제외**하거나, 화면 표시 시 `withoutAddressDetail()`을 통과시킨다. 지금 문서에 이 처리가 없다.

**⑤ AI 지점 ④의 프롬프트 길이**

계약서 필드 16개 + 등기부 필드 + 광고 필드를 한 프롬프트에 넣으면 길어지고 `null` 지시가 묻힌다. **문서 종류별로 프롬프트를 나눈다**(`kind`가 이미 요청에 있다). 종류별 프롬프트는 짧고, 기대 필드만 넣고, `null` 지시를 프롬프트 끝에 다시 한 번 둔다.

## 8. 안정성

### 8-1. v1에서 물려받는 자산

폴백 4종 · 217 유닛 테스트 · `HTTP 200 + {ok:false}` 규약 · 출처 배지가 폴백의 신호 · 스크린샷 러너. **v2의 새 경로에 같은 규약을 그대로 적용**하면 안정성 수준이 유지된다.

### 8-2. 새로 생기는 실패 지점

| 실패 | 폴백 | 사용자에게 보이는 것 | 위험 |
|---|---|---|---|
| PDF에 텍스트 레이어 없음 | 확인 화면 수기 입력 (OCR 보류) | 확인 화면 빈칸 | 낮음 |
| (보류) 기기 OCR 실패·저신뢰 | 동의 후 서버 OCR | 동의 다이얼로그 | — |
| (보류) 서버 OCR 실패·타임아웃·413 | 수기 입력 | 확인 화면 빈칸 | — |
| 구조화 ④ 실패 | 확인 화면 수기 | 배지 `직접 입력` | 낮음 |
| **오프라인 큐 충돌** | "마지막 저장 우선" | **아무것도 안 보임** | ⚠ **중** |
| **IndexedDB 회수·삭제** | 없음 | **원본이 사라짐** | ⚠ **중** |
| 대조 결과 오탐(주소 등) | 없음 | 틀린 "다릅니다" | ⚠ **중** — §3-2로 완화 |
| Neon 콜드 스타트 | 없음 | 첫 요청 지연 | 낮음 (웜업) |

### 8-3. 세 개의 중간 위험에 대한 처치

**오프라인 큐** — "마지막 저장 우선"은 **충돌 시 조용한 유실**을 뜻한다. v1의 "뒤로가기로 방문 기록 유실"과 같은 종류다. 헤더에 **대기 중 항목 수**를 표시하고, 전송 완료 시 사라지게 한다. 유실을 막지는 못해도 보이지 않는 유실은 없앤다.

**IndexedDB 회수** — 문서 목록 화면에 "원본은 이 기기에만 저장되며, 브라우저가 저장 공간을 회수하면 사라질 수 있습니다"를 상시 노출. 사라진 경우 추출된 필드는 서버에 남아 있으므로 **대조 결과는 유지되고 하이라이트만 안 된다** — 이 동작을 코드로 보장한다(원본 없음을 예외가 아니라 정상 상태로 처리).

**대조 오탐** — §3-2. `different`를 내는 필드를 좁히는 것이 유일하게 확실한 방법이다.

## 9. 온디바이스 경계

녹음이 빠지면서 선이 단순해졌고, OCR 보류로 한 번 더 단순해졌다. 구조화가 서버라는 사실은 바뀌지 않는다.

```
기기                          서버
─────────────────────────    ─────────────────────────
원본 PDF·이미지 (IndexedDB)   추출된 필드만
PDF 텍스트 추출 (pdf.js)      구조화 (Gemini, 지점 ④ — 마스킹 후)
bbox 하이라이트               대조 (순수 함수)
오프라인 조사지 (PWA)          질문 생성·금융 계산
(보류) OCR 1차 (Tesseract.js)  ※ 원본은 어떤 경우에도 저장하지 않음
                             ※ (보류) 서버 OCR은 동의 시에만, 처리 후 폐기
```

PDF에 텍스트 레이어가 있으면 **OCR조차 필요 없고 서버로 가는 것은 마스킹된 텍스트뿐**이다. 브라우저 네트워크 탭에서 "이미지 요청이 하나도 없다"로 관측할 수 있다.

**정직하게 말할 것**: "전부 온디바이스"라고 하지 않는다. 서버 OCR을 재개하면 그 경로의 마스킹 불가(§5-4)까지 먼저 말한다.
